# claude-code-container ユースケース定義書

本書は `docs/requirements.md`（要件定義書）で定義した機能を、実際の利用シーンに落とし込んだ
ユースケース集である。各ユースケースは要件定義書の該当セクションと対応付けている。

## 1. 目的

要件定義書の各要件が「誰が」「どのような状況で」「どのように使うか」を具体化し、
実装・レビュー時に要件の過不足を確認できるようにする。

## 2. 登場人物（アクター）

| アクター | 説明 |
| --- | --- |
| 利用者 | Claude Code をコンテナ経由で利用する個人開発者。ホスト（クラウド VM 等）の管理者を兼ねる。 |
| ホスト環境 | コンテナを稼働させるサーバー（クラウド VM やオンプレマシン）。Docker または Podman が動作する。 |
| Claude Code CLI | コンテナ内で稼働する `claude` コマンド本体。 |
| リモートリポジトリ | GitHub 等、作業対象のソースコードを保管する Git ホスティングサービス。 |

## 4. ユースケース詳細

### UC-1: コンテナエンジンを選んでセットアップする

- **アクター**: 利用者
- **事前条件**: ホストに Docker または Podman のいずれかがインストールされている。
- **基本フロー**:
  1. 利用者がリポジトリを取得し、セットアップスクリプトを実行する。
  2. 利用者はコンテナエンジンとして Docker / Podman のいずれを使うかを、環境変数や起動引数で指定する
     （未指定時は Docker をデフォルトとして扱う）。
  3. 指定に応じたイメージビルド・compose 定義でコンテナが構築・起動される。
- **代替フロー**:
  - 指定したコンテナエンジンが未インストールの場合、UC-2 の環境チェックで検出され、セットアップは
    中断される。
- **事後条件**: 選択したコンテナエンジン上で Claude Code コンテナが起動している。
- **関連要件**: 4.8, 4.9

### UC-2: セットアップ前に環境チェックで不備を検出する

- **アクター**: 利用者
- **事前条件**: なし（初回セットアップ前を想定）。
- **基本フロー**:
  1. 利用者が `./scripts/check-env.sh` 等の環境チェックコマンドを実行する（またはセットアップ
     スクリプトから自動的に呼び出される）。
  2. コンテナエンジン・compose ツール・`git` 等必須コマンドの有無やバージョン、
     Anthropic API / claude.ai への到達性が順に検証される。
  3. すべて OK であればセットアップ（イメージビルド・コンテナ起動）が続行される。
- **代替フロー**:
  - いずれかの項目が NG の場合、NG 項目・原因・対処方法（インストールコマンド例等）が表示され、
    セットアップは中断される。利用者は指示に従って環境を修正し、再実行する。
- **事後条件**: ホスト環境がセットアップ要件を満たしていることが確認できている。
- **関連要件**: 4.9

### UC-3: リモート VM 上でコンテナに常駐させ SSH でアタッチする

- **アクター**: 利用者
- **事前条件**: クラウド VM 等のホストが用意され、UC-1 のセットアップが完了している。
- **基本フロー**:
  1. 利用者はコンテナを `restart: unless-stopped` 相当のポリシーで起動する。
  2. 利用者は別端末から SSH でホストに接続し、`docker exec` / `podman exec` でコンテナ内シェルに
     アタッチする。
  3. `tmux` セッション内で `claude` コマンドを実行し、対話的にやり取りする。
  4. 作業を中断する場合は `tmux` セッションをデタッチしたまま SSH 接続を切断する。
- **事後条件**: コンテナはバックグラウンドで稼働を継続し、次回接続時に同じ `tmux` セッションへ
  再アタッチできる。
- **関連要件**: 4.4, 4.5

### UC-4: 1台のホストで複数プロジェクトを並行利用する

- **アクター**: 利用者
- **事前条件**: ホストに UC-1 のセットアップ済み環境がある。
- **基本フロー**:
  1. 利用者はプロジェクト A 用のコンテナ・ボリュームをセットアップする。
  2. 同一ホスト上でプロジェクト B 用に、別名のコンテナ・ボリュームをもう一組セットアップする。
  3. 各コンテナは認証情報・作業ディレクトリを独立したボリュームで保持し、互いに影響しない。
- **事後条件**: プロジェクト A・B が同一ホスト上で独立に稼働し、一方の変更が他方に波及しない。
- **関連要件**: 3.1, 4.5

### UC-5: 認証情報を永続化し再ログインなしで使い続ける

- **アクター**: 利用者
- **事前条件**: UC-1 の初回セットアップが完了している。
- **基本フロー**:
  1. 利用者は初回起動時にコンテナ内で `claude login` 相当の OAuth 認証を行う。
  2. 認証情報は `~/.claude` 等、ボリュームマウントされたディレクトリに保存される。
  3. 利用者がコンテナを破棄し、同じボリュームを指定して再作成する。
  4. 再起動後のコンテナで `claude` を実行しても、再ログインなしで利用を継続できる。
- **代替フロー**: `ANTHROPIC_API_KEY` を利用する場合は OAuth ログインを行わずに認証できる。
- **事後条件**: コンテナの破棄・再作成をまたいで認証状態が保持されている。
- **関連要件**: 4.3, 4.5

### UC-6: 自動承認モードで指示を連続実行する（web 版ライク）

- **アクター**: 利用者
- **事前条件**: コンテナが起動し、対象リポジトリへのアクセス権（後述 UC-7 の認証情報）がある。
- **基本フロー**:
  1. 利用者は自動承認モード（`claude code on the web` 相当、非対話実行）でコンテナを起動する。
  2. 利用者は自然文で指示（例:「〇〇機能を追加して」）を送る。
  3. Claude Code はコマンド実行・ファイル編集のたびに承認を求めることなく、一連の作業を最後まで
     自律的に実行する。
  4. 利用者は結果を確認し、続けて次の指示を送る。
- **代替フロー**: 破壊的な操作（force push 等）が必要な場合でも自動では実行せず、5.1 の方針に従い
  デフォルトでは回避する。
- **事後条件**: 利用者は個々のコマンド実行を承認する手間なく、一連のタスクを完了できる。
- **関連要件**: 4.10, 5.1

### UC-7: 対話セッションごとにブランチを切り、指示のたびに自動で commit / push される

> **用語メモ**: ここでの「対話セッション」は Claude Code との1回の会話単位（＝1タスク）を指し、
> UC-8・UC-9 で扱う `tmux` / SSH の接続セッションとは別概念である。SSH・`tmux` の接続を切断／
> 再接続しても、Claude Code との対話セッション自体（＝作業中のブランチ）は継続する。

- **アクター**: 利用者
- **事前条件**: コンテナのセットアップ時に対象リポジトリが `git clone` 済みである。push 用の
  認証情報（GitHub PAT や SSH 鍵）がボリューム経由で利用可能である。
- **基本フロー**:
  1. 利用者が Claude Code との新しい対話セッションを開始し、依頼を送る。
  2. Claude Code はベースブランチ（`main` 等）から、そのセッション用の新規ブランチを作成する。
  3. Claude Code が指示に基づきコードを変更し、変更内容を自動的に `git commit` してセッション用
     ブランチへ `git push` する。
  4. 利用者は結果を確認し、同じ対話セッション内で追加の指示（修正依頼等）を送る。
  5. Claude Code は新しいブランチを切らずに、同じセッション用ブランチ上で変更・commit・push を
     繰り返す（1つの対話セッションで指示が複数回にわたるケース）。
  6. 対話セッションが完了したら、利用者はリモートリポジトリ側でブランチの差分・PR を確認する。
     次に新しい依頼をする際は、新しい対話セッションを開始し、手順2に戻って新規ブランチが切られる。
- **代替フロー**:
  - push がコンフリクトや認証エラーで失敗した場合、エラー内容が利用者に提示され、次の指示までの
    間、変更はローカルのコミットとして保持される。
  - 同一の対話セッション中に、別のリポジトリやブランチへ途中から切り替えることは想定しない
    （新しい対象で作業する場合は、新しい対話セッションを開始する）。
- **事後条件**: 対話セッションの区切りごとに独立したブランチが作られ、各ブランチには当該セッション
  中の指示すべてに対応するコミット履歴がリモートへ反映されている。利用者は都度手動でコミットする
  必要がない。
- **関連要件**: 4.11

### UC-8: セッション切断後に作業を再開する

- **アクター**: 利用者
- **事前条件**: UC-3 の要領でコンテナ内 `tmux` セッションが稼働中である。
- **基本フロー**:
  1. 利用者の SSH 接続がネットワーク断等で予期せず切れる。
  2. 利用者が再度ホストに SSH 接続し、`tmux attach` で元のセッションに再接続する。
  3. 切断前に実行中だった `claude` セッションの出力・状態がそのまま表示され、作業を継続できる。
- **事後条件**: ネットワーク切断があっても作業内容・対話履歴が失われない。
- **関連要件**: 4.4

### UC-9: ホスト再起動後にワンコマンドで環境を復旧する

- **アクター**: 利用者
- **事前条件**: UC-1 のセットアップ済み環境があり、`restart: unless-stopped` 等のポリシーが
  設定されている。
- **基本フロー**:
  1. ホスト（クラウド VM）がメンテナンス等で再起動される。
  2. ホスト起動後、Docker/Podman サービスが自動起動し、コンテナも自動的に再起動する。
  3. 自動起動しない場合、利用者は `docker compose up -d` / `podman-compose up -d` を実行し、
     コンテナを復旧する。
  4. UC-3・UC-5 の要領でアタッチし、認証情報・作業内容が保持されたまま作業を再開できる。
- **事後条件**: ホスト再起動後も、単純な操作のみで元の作業環境に復帰できる。
- **関連要件**: 5.2

### UC-10: Podman 環境（rootless）で Docker 非対応ホストでも利用する

- **アクター**: 利用者
- **事前条件**: ホストに Docker がインストールできない、または rootless 運用が求められる
  （例: 会社支給端末で sudo 権限がない、セキュリティポリシー上 Docker デーモンの常駐が禁止されている）。
- **基本フロー**:
  1. 利用者は Podman をユーザー権限のみでインストールする。
  2. UC-1 の要領で、コンテナエンジンとして Podman を指定してセットアップする。
  3. UC-2 の環境チェックで Podman・`podman-compose` の有無が確認される。
  4. rootless モードでコンテナが起動し、ボリュームマウント時は SELinux ラベル等の差異が
     起動スクリプト側で吸収される。
- **事後条件**: root 権限や Docker デーモンなしに、Docker 版と同等の使用感で環境を利用できる。
- **関連要件**: 4.8, 5.1

## 5. 対象外のユースケース（参考）

以下は要件定義書 2章・3.2 で対象外とされているシーンであり、本書でも扱わない。

- CI/CD パイプラインからの非対話バッチ実行。
- ローカル PC 上での VSCode Dev Containers 連携。
- 複数利用者間での権限分離・監査ログを前提とした運用。
