# claude-code-container 要件定義書

## 1. 目的・背景

Claude Code をコンテナ内で自由に実行できる環境を構築する。
ローカル環境を汚さず、また複数のプロジェクト・利用者間で環境を分離した上で、
Claude Code を継続的に稼働させられる「コンテナ艦橋」を提供することを目的とする。

## 2. 想定利用シーン

- リモートサーバー（クラウド VM など）上にコンテナを常駐させ、SSH または Web 経由でアタッチして
  Claude Code と対話的にやり取りする。
- 1台のホスト上で複数のコンテナ（プロジェクト単位・用途単位）を並行稼働させることを想定する。

対象外とするシーン（本要件定義書のスコープ外）:

- CI/CD パイプラインからの非対話的なバッチ実行（将来的な拡張候補とし、本フェーズでは扱わない）。
- ローカル PC 上での VSCode Dev Containers 連携（将来的な拡張候補）。

## 3. スコープ

### 3.1 対象

- Claude Code CLI を実行できる Docker コンテナイメージ（Dockerfile）一式。
- コンテナを常駐させ、外部からアタッチ／再接続するための構成（docker-compose、起動スクリプト等）。
- 認証情報・作業データを永続化するためのボリューム設計。

### 3.2 対象外

- ホスト側（クラウド VM）のプロビジョニングやネットワーク構築そのもの（既存のサーバーがある前提）。
- マルチユーザーでの権限分離・監査ログ基盤（個人利用を優先し、厳格な統制は求めない）。

## 4. 機能要件

### 4.1 ベースイメージ・OS

- Debian または Ubuntu の LTS 系イメージをベースとする。
- Claude Code CLI の動作要件（Node.js 18 以上）を満たすこと。

### 4.2 Claude Code CLI

- コンテナイメージに Claude Code CLI をインストール済みの状態で提供する。
- `claude` コマンドがそのまま実行できること。
- バージョン更新はイメージの再ビルドで追従できること（固定バージョン指定 or 最新版取得を選択可能にする）。

### 4.3 認証

- 認証方式は Claude.ai アカウントによる OAuth ログイン（`claude login` 相当のブラウザ認証フロー）を採用する。
- 認証情報（トークン等）はコンテナのライフサイクルに依存せず永続化し、コンテナ再作成後も再ログイン不要で
  利用を継続できること（`~/.claude` 等の認証情報ディレクトリをボリュームマウントする）。
- API キー（`ANTHROPIC_API_KEY`）による認証を妨げない構成とし、必要に応じて併用・切り替えできること。

### 4.4 常駐・リモートアクセス

- コンテナはフォアグラウンドプロセスを持たせて常駐させる（例: `tail -f /dev/null` やシェル待受、
  もしくは `docker run -d` + `restart: unless-stopped` 相当のポリシー）。
- 利用者はコンテナ起動後、`docker exec` または SSH 経由でシェルにアタッチし、`claude` コマンドを対話的に
  実行できること。
- 長時間セッションの途中切断・再接続に耐えられるよう、`tmux` または `screen` をコンテナに同梱し、
  セッションを維持できるようにする。
- ホストの再起動やコンテナの再起動が発生しても、作業内容（プロジェクトファイル・認証情報・シェル履歴）が
  失われないこと。

### 4.5 データ永続化

- 以下をホスト側ボリュームとしてマウントし、コンテナの破棄・再作成に対して永続化する。
  - Claude Code の認証情報・設定ディレクトリ（`~/.claude` 等）
  - 作業用リポジトリ・プロジェクトディレクトリ（`/workspace` 等）
  - シェル履歴・dotfiles（任意）
  - Git の設定（`~/.gitconfig`、SSH 鍵 等）
- ボリュームはコンテナ単位（プロジェクト単位）で分離できること。

### 4.6 同梱する開発ツール・ランタイム

- Node.js / npm（Claude Code CLI 本体の実行に必須）
- Git
- GitHub CLI（`gh`）
- Python および pip（対象プロジェクトの言語に応じて利用）
- 上記以外に必要なツールは、都度 Dockerfile に追加できる拡張性を持たせる。

### 4.7 ネットワーク

- Claude Code の API 通信（Anthropic API / claude.ai への OAuth 通信）に必要なアウトバウンド通信を許可する。
- 特別なプロキシやサンドボックス制御は本フェーズでは必須としない（4.8 参照）。

## 5. 非機能要件

### 5.1 セキュリティ・権限

- コンテナ内のプロセスは非 root ユーザーで実行する（`sudo` 権限は必要最小限、または付与しない）。
- 個人利用を主目的とするため、コマンド実行やネットワークアクセスに対する厳格なサンドボックス化・
  制限は必須としない。手軽に使えることを優先する。
- 認証情報を含むボリューム・ファイルはホスト側でアクセス権限を適切に設定する（パーミッション 600 等）。

### 5.2 可用性・運用性

- コンテナ・ホストの予期しない再起動後も、`docker compose up -d` 等の単純な操作で環境を復旧できること。
- コンテナのログは標準出力または永続化されたログファイルで確認できること。

### 5.3 保守性

- Dockerfile / docker-compose.yml はバージョン管理し、変更履歴を追えること。
- Claude Code CLI やベースイメージのバージョンアップに追従しやすい構成にする。

### 5.4 移植性

- 特定のクラウドベンダーに依存しない、標準的な Docker / docker-compose ベースの構成とする。

## 6. 構成イメージ（案）

```
claude-code-container/
├── Dockerfile              # Claude Code CLI + 開発ツールを含むイメージ定義
├── docker-compose.yml      # 常駐起動・ボリュームマウント定義
├── docs/
│   └── requirements.md     # 本要件定義書
└── README.md
```

- `docker-compose.yml` で以下を定義する想定:
  - サービス本体（`restart: unless-stopped`）
  - ボリューム: 認証情報用・ワークスペース用
  - 必要に応じたポート公開（SSH 経由でアタッチする場合）

## 7. 前提条件・制約

- 利用者は Claude.ai の有効なアカウント（Pro/Max 等、Claude Code が利用可能なプラン）を保持していること。
- ホスト側に Docker および docker-compose（または互換ツール）がインストールされていること。
- コンテナはインターネットに接続できる環境で稼働させること。

## 8. 今後の検討事項（オープン課題）

- SSH アクセスを提供する場合の鍵配布・ポート管理方法。
- 複数プロジェクト・複数コンテナを運用する際の命名規則・管理方法。
- 将来的な CI/CD 連携（API キー認証での非対話実行）や VSCode Dev Containers 対応の要否。
- リソース（CPU/メモリ/ディスク）上限の設定要否。
