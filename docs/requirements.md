# claude-code-container 要件定義書

## 1. 目的・背景

Claude Code をコンテナ内で自由に実行できる環境を構築する。
ローカル環境を汚さず、また複数のプロジェクト・利用者間で環境を分離した上で、
Claude Code を継続的に稼働させられる「コンテナ艦橋」を提供することを目的とする。

## 2. 想定利用シーン

- リモートサーバー（クラウド VM など）上にコンテナを常駐させ、SSH または Web 経由でアタッチして
  Claude Code と対話的にやり取りする。
- 1台のホスト上で複数のコンテナ（プロジェクト単位・用途単位）を並行稼働させることを想定する。

対象外とするシーン（本要件定義書のスコープ外）:

- CI/CD パイプラインからの非対話的なバッチ実行（将来的な拡張候補とし、本フェーズでは扱わない）。
- ローカル PC 上での VSCode Dev Containers 連携（将来的な拡張候補）。

## 3. スコープ

### 3.1 対象

- Claude Code CLI を実行できるコンテナイメージ（Dockerfile）一式。
- コンテナエンジンとして Docker に加え Podman を選択できる構成（compose 定義、起動スクリプト等）。
- コンテナを常駐させ、外部からアタッチ／再接続するための構成（docker-compose／podman-compose、起動スクリプト等）。
- 認証情報・作業データを永続化するためのボリューム設計。
- セットアップ実行前にホスト環境の要件充足を確認する環境チェック機能。

### 3.2 対象外

- ホスト側（クラウド VM）のプロビジョニングやネットワーク構築そのもの（既存のサーバーがある前提）。
- マルチユーザーでの権限分離・監査ログ基盤（個人利用を優先し、厳格な統制は求めない）。

## 4. 機能要件

### 4.1 ベースイメージ・OS

- Debian または Ubuntu の LTS 系イメージをベースとする。
- Claude Code CLI の動作要件（Node.js 18 以上）を満たすこと。

### 4.2 Claude Code CLI

- コンテナイメージに Claude Code CLI をインストール済みの状態で提供する。
- `claude` コマンドがそのまま実行できること。
- バージョン更新はイメージの再ビルドで追従できること（固定バージョン指定 or 最新版取得を選択可能にする）。

### 4.3 認証

- 認証方式は Claude.ai アカウントによる OAuth ログイン（`claude login` 相当のブラウザ認証フロー）を採用する。
- 認証情報（トークン等）はコンテナのライフサイクルに依存せず永続化し、コンテナ再作成後も再ログイン不要で
  利用を継続できること（`~/.claude` 等の認証情報ディレクトリをボリュームマウントする）。
- API キー（`ANTHROPIC_API_KEY`）による認証を妨げない構成とし、必要に応じて併用・切り替えできること。

### 4.4 常駐・リモートアクセス

- コンテナはフォアグラウンドプロセスを持たせて常駐させる（例: `tail -f /dev/null` やシェル待受、
  もしくは `docker run -d` / `podman run -d` + `restart: unless-stopped` 相当のポリシー）。
- 利用者はコンテナ起動後、`docker exec` / `podman exec` または SSH 経由でシェルにアタッチし、`claude`
  コマンドを対話的に実行できること。
- 長時間セッションの途中切断・再接続に耐えられるよう、`tmux` または `screen` をコンテナに同梱し、
  セッションを維持できるようにする。
- ホストの再起動やコンテナの再起動が発生しても、作業内容（プロジェクトファイル・認証情報・シェル履歴）が
  失われないこと。

### 4.5 データ永続化

- 以下をホスト側ボリュームとしてマウントし、コンテナの破棄・再作成に対して永続化する。
  - Claude Code の認証情報・設定ディレクトリ（`~/.claude` 等）
  - 作業用リポジトリ・プロジェクトディレクトリ（`/workspace` 等）
  - シェル履歴・dotfiles（任意）
  - Git の設定（`~/.gitconfig`、SSH 鍵 等）
- ボリュームはコンテナ単位（プロジェクト単位）で分離できること。

### 4.6 同梱する開発ツール・ランタイム

- Node.js / npm（Claude Code CLI 本体の実行に必須）
- Git
- GitHub CLI（`gh`）
- Python および pip（対象プロジェクトの言語に応じて利用）
- 上記以外に必要なツールは、都度 Dockerfile に追加できる拡張性を持たせる。

### 4.7 ネットワーク

- Claude Code の API 通信（Anthropic API / claude.ai への OAuth 通信）に必要なアウトバウンド通信を許可する。
- 特別なプロキシやサンドボックス制御は本フェーズでは必須としない。

### 4.8 コンテナエンジンの選択

- コンテナエンジンとして Docker（Docker Engine + docker compose）をデフォルトとしつつ、
  Podman（`podman` + `podman-compose` もしくは `podman compose`）を選択できること。
- 利用者は環境変数・設定ファイル・起動スクリプトの引数等により、セットアップ時にどちらの
  コンテナエンジンを使用するか選択できること。
- Podman を選択した場合、rootless 実行を基本とする。ボリュームマウント時の SELinux ラベル
  （`:Z`／`:z`）付与やネットワークモードの違いなど、Docker との差異を起動スクリプト側で吸収すること。
- compose 定義（`docker-compose.yml` 等）は、選択したコンテナエンジンでそのまま利用できるか、
  エンジンごとに互換性のある構成を用意すること。
- 一部エンジン固有の機能に依存する場合は、その旨をドキュメントに明記し、代替手段を示すこと。

### 4.9 セットアップ前環境チェック

- セットアップスクリプト（イメージビルド・コンテナ起動）を実行する前に、ホスト環境が要件を
  満たしているかを自動検証する「環境チェック」機能を提供する。
- 環境チェックの主な確認項目:
  - 選択したコンテナエンジン（Docker または Podman）がインストール済みであり、動作要件を満たす
    バージョンであること。
  - compose 相当のツール（`docker compose` / `podman-compose` 等）が利用可能であること。
  - `git` など、セットアップに必要なコマンドが PATH 上に存在すること。
  - ホストのディスク空き容量・メモリなど、必要に応じた最低リソース要件を満たすこと。
  - Anthropic API / claude.ai への到達性（インターネット接続）を確認できること。
- チェック結果は項目ごとに OK / NG を分かりやすく出力し、NG の場合は原因と対処方法（インストール
  手順・設定変更方法等）を提示すること。
- 必須項目に NG がある場合はセットアップ処理を中断し、利用者が対処してから再実行できるようにする
  こと。
- 環境チェックは単体のスクリプト／コマンドとして提供し、セットアップフロー（README の手順や
  起動スクリプト）に組み込むこと（例: `./scripts/check-env.sh`）。

### 4.10 実行時の承認方式（非対話・自動承認実行）

- `claude code on the web` と同様に、コマンド実行のたびに逐一承認を求めない自動承認モード
  （例: `--dangerously-skip-permissions` 相当のオプション、非対話実行）をデフォルトの実行方式
  として選択できること。
- 承認プロンプトによる中断なく、利用者からの指示に対して Claude Code が一連の作業（コマンド実行・
  ファイル編集・Git 操作等）を自律的に最後まで実行できること。
- 自動承認は 5.1 のセキュリティ要件（非 root ユーザー実行、ボリューム権限設定等）と組み合わせて
  運用することを前提とし、必要に応じて承認確認ありの対話モードにも切り替えられることが望ましい。

### 4.11 Git ワークフロー（自動 clone・タスク単位のブランチ作成・commit / push）

- コンテナのセットアップ時（初回起動時）に、対象リポジトリを一度だけ `git clone` して作業用
  ディレクトリに配置すること。以降、稼働中のコンテナで別のリポジトリへ切り替えることは想定しない。
- 利用者から新しい依頼（タスク）を受け付けるたびに、ベースブランチ（`main` 等）から新規ブランチを
  作成（`git checkout -b`）すること（ブランチ名は用途・日時等から自動生成する、または利用者が
  指定できることが望ましい）。
- 1つのタスクは1回とは限らず、複数回の指示（やり取り）にまたがる場合がある。その間は新しい
  ブランチを切らず、同一のタスク用ブランチ上で作業を継続すること。稼働中のコンテナで別ブランチへ
  途中から切り替えることは想定しない。
- タスク用ブランチ上で、指示を受けて変更を行うたびに、その変更内容を `git commit` し、リモートへ
  `git push` すること。人手による都度のコミット操作を必要としない。
- 「新しいタスクが始まった」と判定し新規ブランチを切るタイミング（利用者からの明示的な新規依頼の
  合図、対話セッションの区切り 等）の具体的な判定方法は運用ルールとして別途定義すること。
- push 先で利用する認証情報（GitHub PAT や SSH 鍵等）は 4.5 のデータ永続化・ボリューム設計を利用し、
  コンテナ再作成後も再設定不要で利用できること。
- push が失敗した場合（コンフリクト、認証エラー、ネットワーク断等）の挙動（リトライ、エラー内容の
  提示、次の指示までの保留 等）を定義すること。

## 5. 非機能要件

### 5.1 セキュリティ・権限

- コンテナ内のプロセスは非 root ユーザーで実行する（`sudo` 権限は必要最小限、または付与しない）。
- 個人利用を主目的とするため、コマンド実行やネットワークアクセスに対する厳格なサンドボックス化・
  制限は必須としない。手軽に使えることを優先する。
- 認証情報を含むボリューム・ファイルはホスト側でアクセス権限を適切に設定する（パーミッション 600 等）。
- 4.10 の自動承認モードはコマンド実行の逐一確認を省略するため、誤操作・意図しない変更のリスクが
  相対的に高まることを踏まえ、対象リポジトリ・作業ブランチの分離（4.11）や非 root 実行と併用する
  ことでリスクを低減する。破壊的操作（force push 等）をデフォルトで避けるなど、運用上の配慮を行う。

### 5.2 可用性・運用性

- コンテナ・ホストの予期しない再起動後も、`docker compose up -d` / `podman-compose up -d` 等の
  単純な操作で環境を復旧できること。
- コンテナのログは標準出力または永続化されたログファイルで確認できること。

### 5.3 保守性

- Dockerfile / docker-compose.yml はバージョン管理し、変更履歴を追えること。
- Claude Code CLI やベースイメージのバージョンアップに追従しやすい構成にする。

### 5.4 移植性

- 特定のクラウドベンダーに依存しない、標準的な Docker / Podman ベースの構成とし、いずれの
  コンテナエンジンでも同等の手順で利用できること。

## 6. 構成イメージ（案）

```
claude-code-container/
├── Dockerfile              # Claude Code CLI + 開発ツールを含むイメージ定義
├── docker-compose.yml      # 常駐起動・ボリュームマウント定義（Docker / Podman 両対応）
├── scripts/
│   └── check-env.sh        # セットアップ前環境チェックスクリプト
├── docs/
│   └── requirements.md     # 本要件定義書
└── README.md
```

- `docker-compose.yml` で以下を定義する想定:
  - サービス本体（`restart: unless-stopped`）
  - ボリューム: 認証情報用・ワークスペース用
  - 必要に応じたポート公開（SSH 経由でアタッチする場合）
  - `docker compose` / `podman-compose`（または `podman compose`）のいずれでも起動できる構成
- `scripts/check-env.sh` で以下を検証する想定:
  - 選択したコンテナエンジン（Docker / Podman）および compose ツールの有無・バージョン
  - 必須コマンド（`git` 等）の有無
  - Anthropic API / claude.ai への到達性

## 7. 前提条件・制約

- 利用者は Claude.ai の有効なアカウント（Pro/Max 等、Claude Code が利用可能なプラン）を保持していること。
- ホスト側に Docker（および docker-compose）、または Podman（および podman-compose 等の互換ツール）の
  いずれかがインストールされていること。
- コンテナはインターネットに接続できる環境で稼働させること。

## 8. 今後の検討事項（オープン課題）

- SSH アクセスを提供する場合の鍵配布・ポート管理方法。
- 複数プロジェクト・複数コンテナを運用する際の命名規則・管理方法。
- 将来的な CI/CD 連携（API キー認証での非対話実行）や VSCode Dev Containers 対応の要否。
- リソース（CPU/メモリ/ディスク）上限の設定要否。
- Docker と Podman 間でのイメージ・ボリュームの相互運用性（移行時の互換性）の検証要否。
- 自動 commit / push の粒度（1指示につき1コミットとするか、変更のまとまり単位とするか）の方針。
- 自動 push 時にプルリクエスト作成やレビュー依頼まで自動化するか、push までに留めるかの範囲。
- 自動承認モードにおける操作範囲の制限（実行禁止コマンドのブロックリスト等）の要否。
- 「新しいタスクの開始」をシステム的にどう判定し、新規ブランチ作成のトリガーとするかの具体的な方法
  （利用者による明示的な合図か、対話セッション単位か 等）。
